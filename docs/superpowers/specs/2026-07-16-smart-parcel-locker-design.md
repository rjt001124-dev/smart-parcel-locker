# 智能快递柜系统设计规格

- 日期：2026-07-16
- 仓库：`rjt001124-dev/smart-parcel-locker`
- 后端框架：Go Kratos
- 交付策略：Monorepo、模块化单体起步、分阶段演进
- 需求来源：智能快寄柜 01—10 号任务工单

## 1. 项目目标

建设一套可部署、可审计、可扩展的智能快递柜系统，完成用户查找寄存点、选择柜格、计费支付、存入、查看订单、补缴、取出和售后闭环，并向运营人员提供网点、柜机、订单、支付、通知和设备告警管理能力。

系统应优先保证订单、资金和柜格状态一致性。Coze 数字人、Go 性能工具链和设备运维智能体在核心业务稳定后接入，不得影响首期业务闭环。

- 个人中心、头像、服务入口和退出登录

### 2.2 第二阶段：生产能力

- 高风险设备操作人工确认、审计和追踪

## 3. 总体架构

第一阶段采用模块化单体，而不是立即拆分微服务。Kratos API 服务负责同步请求，Worker 负责支付回调后续任务、通知重试、订单超时和补缴提醒。各领域通过明确接口和事务事件协作，为后续拆分服务保留边界。

```text
微信小程序 ─┐
React 后台 ─┼─ HTTPS/WebSocket ─ Nginx ─ Kratos API
Coze/数字人 ┘                              │
                         ┌─────────────────┼─────────────────┐
                         │                 │                 │
                    MySQL               Redis             Worker
                         │                 │                 │
                         └──── 支付宝 / 设备网关 / 通知渠道 ──┘
```

## 4. Kratos 分层约束

每个领域模块遵循 Kratos 分层：

- `service`：协议适配、身份提取、输入校验和输出转换。
- `biz`：实体、用例、状态机、领域规则和仓储接口。
- `data`：数据库、缓存、外部支付和设备适配实现。
- `server`：HTTP、gRPC、中间件和路由注册。
- `conf`：配置结构和环境注入。

传输层不得直接访问数据库；数据层不得决定订单业务状态；支付和设备 SDK 必须通过接口注入，便于沙箱、模拟和测试。

## 5. 核心领域

### 5.1 身份与权限

- 小程序用户通过受控登录流程建立会话。
- 管理后台采用管理员账户、JWT/会话和 RBAC。
- 权限至少区分运营管理员、网点管理员和只读审计人员。
- 退出登录必须撤销或失效刷新令牌并记录日志。

### 5.2 网点、柜机与柜格

- 城市包含名称、代码、省份和启用状态。
- 网点包含地址、坐标、营业时间、联系方式和服务状态。
- 柜机包含设备编号、网点、协议类型、网络状态和最后心跳。
- 柜格包含尺寸、占用状态、柜门状态和当前订单。
- 柜格从空闲转为锁定必须使用事务条件更新，防止并发重复分配。

### 5.3 计费

- 计费规则支持柜格尺寸、按小时/天计费、押金、免费时长、超时费和优惠叠加限制。
- 下单时保存计费快照，后续规则变化不得修改历史订单金额。
- 金额统一使用最小货币单位整数表示，禁止使用浮点数。

### 5.4 支付与账务

- 支付订单和业务订单分离。
- 支付回调必须验签、校验商户、金额、订单号和回调状态。
- 外部交易号和回调幂等键必须唯一。
- 资金流水只追加、不修改，覆盖充值、消费、退款和人工调整。
- 支付成功不代表寄存成功；柜格分配或开门最终失败时进入退款流程。

### 5.5 通知

- 统一事件模型包含事件类型、接收人、模板、变量、优先级和幂等键。
- 支持站内信、短信、邮件和回调渠道扩展。
- 支持去重、频控、重试、升级、人工补发和完整投递审计。
- 首期覆盖支付结果、取件提醒、订单完成、订单超时、柜门未关和设备异常。

### 5.6 设备指令

- 每条指令具有唯一编号、设备编号、动作、参数、有效期和执行状态。
- 开门指令必须限制重试次数并防止重复执行。
- 首期模拟设备网关必须复现在线、离线、超时、失败和柜门未关场景。
- 重启、隔离、限流和回滚等高风险动作必须人工确认并记录审计。

## 6. 订单状态机

```text
待支付 ──支付成功──> 已支付 ──分配柜格──> 待存入
   │                    │                    │
   └─取消/超时─> 已取消  └─无柜格─> 待退款  ├─开门成功并关门─> 寄存中
                                             └─设备失败─> 开门异常

寄存中 ──发起取件──> 待取件 ──取件并关门──> 已完成
   │
   └─超时──> 待补缴 ──补缴成功──> 待取件

待退款 ──退款回调成功──> 已退款
```

状态迁移必须由用例方法执行并验证来源状态。每次迁移写入 `order_status_logs`，包含操作者、原因、时间、请求幂等键和关联设备/支付事件。

## 8. 核心寄存数据流

1. 用户定位城市并查询附近寄存点。
2. 用户选择网点、柜格尺寸和寄存时长。
3. 后端锁定一个空闲柜格并设置短期占用期限。
4. 计费服务生成租金、押金、优惠和应付金额快照。
5. 创建业务订单与支付宝支付订单。
6. 支付宝异步回调通过验签和幂等校验后写入支付流水。
7. 订单进入已支付，系统确认柜格锁定并生成开门指令。
8. 柜门开启并关闭后，订单进入寄存中，柜格进入占用。
9. 超时任务生成提醒或待补缴状态。
10. 用户完成补缴后发起取件，设备再次开门。
11. 柜门关闭后订单完成，柜格释放为空闲。

补偿规则：支付后无可用柜格时进入退款；设备短暂失败允许受控重试或换柜；设备最终失败进入退款并生成管理员告警。

## 9. 错误处理

API 返回统一错误结构，包括业务错误码、用户可读消息、请求追踪 ID 和可重试标记。内部堆栈、SQL、密钥和设备底层凭证不得返回前端。

核心错误码：

- `ORDER_STATE_CONFLICT`
- `LOCKER_CELL_OCCUPIED`
- `LOCKER_DEVICE_OFFLINE`
- `DEVICE_COMMAND_TIMEOUT`
- `PAYMENT_SIGNATURE_INVALID`
- `PAYMENT_CALLBACK_DUPLICATED`
- `PAYMENT_AMOUNT_MISMATCH`
- `COUPON_NOT_APPLICABLE`
- `ORDER_OVERDUE_PAYMENT_REQUIRED`

前端根据错误码提供可执行操作，如重新选择柜格、重新支付、补缴、稍后重试或联系管理员。

## 10. Figma 与前端设计

Figma 是前端实现和视觉验收的唯一基准。文件结构：

- `00 Foundations`：颜色、字体、字号、间距、圆角、阴影和图标。
- `01 Components`：按钮、输入、选择、卡片、状态、弹窗、表格和导航。
- `02 Mini App`：首页、城市、网点、柜格、支付、订单、取件和个人中心。
- `03 Admin Web`：概览、网点、柜机、订单、支付、通知、权限和审计。

用户端采用蓝白专业风格和充足留白；后台采用深色导航与浅色内容区。保留工单的业务信息结构，统一组件、排版和交互。

所有关键页面必须覆盖正常、加载、空数据、网络失败、支付失败、支付处理中、柜格被抢占、设备离线、开门失败、柜门未关、订单超时、补缴成功和权限不足状态。

## 13. 可观测与性能

- Kratos 中间件生成和传播请求追踪 ID。
- Prometheus 暴露请求量、延迟、错误率、数据库和业务指标。
- Grafana 展示订单、支付、设备和通知面板。
- 受保护的 pprof、trace 和 runtime/metrics 端点用于诊断。
- Pyroscope 或 Parca 用于低开销持续性能分析。
- 性能分析接口必须限制权限，采样对业务性能影响低于 3%。

## 14. CI/CD 与部署

GitHub Actions 执行：

1. Go 格式、静态分析和测试。
2. Proto 兼容性检查。
3. 数据库迁移验证。
4. 前端 lint、类型检查和测试。
5. 小程序和管理后台构建。
6. Docker 镜像构建和依赖安全扫描。
7. 主分支部署测试环境。
8. 人工批准后发布生产。

第一阶段采用 Docker Compose，包含 Nginx、API、Worker、MySQL、Redis、Prometheus、Grafana 和 Pyroscope。生产规模扩大后迁移 Kubernetes，但不在 MVP 阶段引入不必要复杂度。

部署交付物包含 `.env.example`、数据库迁移、初始化管理员命令、健康检查、备份恢复、日志轮转、HTTPS 配置、回滚脚本和上线检查清单。

## 15. 安全与审计

- 密钥和证书通过环境变量或密钥管理系统注入。
- 支付回调强制验签、金额校验和防重放。
- 用户手机号、设备凭证和支付信息按最小权限访问。
- 管理操作、设备指令、资金调整和智能体建议均记录审计。
- 高风险运维动作必须人工确认，智能体不得绕过确认直接执行。
- 日志脱敏，不记录令牌、完整手机号、私钥或支付证书。

## 16. 验收标准

- 核心寄存链路在支付沙箱和模拟设备环境中端到端通过。
- 并发请求不能重复分配同一柜格。
- 重复支付回调不能重复入账或重复推进订单。
- 订单、支付、设备和通知事件均可审计追踪。
- 小程序和后台页面与批准的 Figma 原型一致。
- 所有首期关键错误状态有明确用户提示和恢复路径。
- CI 检查通过后才能合并主分支。
- Docker Compose 可在全新环境完成初始化和健康检查。

## 17. 实施分解

总体规格不作为一次性大爆炸开发计划。实施按可独立验收的里程碑分别编写计划、开发、测试和提交：

1. 工程基线：Monorepo、Kratos 骨架、AGENTS.md、首个经过验证的 Skill、CI 基础。
2. 设计基线：Figma Foundations、组件库、用户端和后台核心流程原型。
3. 站点与设备：城市、网点、柜机、柜格和模拟设备网关。
4. 寄存订单：计费、柜格锁定、订单状态机、存入和取件。
5. 支付账务：支付宝沙箱、回调、流水、退款、续费和补缴。
6. 用户体验：首页、订单、个人中心、通知和管理后台。
7. 上线能力：可观测、压力测试、安全检查、部署、备份和回滚。
8. AI 扩展：数字人、其余项目 Skills 和设备运维智能体。

下一个实施计划只覆盖里程碑 1；每个后续里程碑在前一阶段通过验收后单独规划，避免跨阶段耦合和未验证范围膨胀。

## 18. 明确不在 MVP 内的内容

- 同时适配多个真实柜机厂商协议
- 生产级 Kubernetes 多集群
- AI 自动执行高风险设备操作
- 完整数字人商业化能力
- 与核心寄存闭环无关的社交、营销或复杂会员体系

这些内容保留扩展接口，但不得延迟第一阶段交付。
