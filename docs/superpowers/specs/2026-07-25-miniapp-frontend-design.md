# 智能快递柜小程序前端设计

## 1. 目标与范围

第一阶段交付智能快递柜微信小程序用户端，完成“找柜→选柜格→支付→存件→查看订单→取件”业务闭环。本阶段同时纳入消息通知、扫码找柜和柜门安全提醒。

第一阶段不实现管理后台、营销活动、会员等级或多平台发布。管理后台在小程序主流程验收后进入第二阶段。

## 2. 产品与视觉方向

采用已批准的“服务任务型”首页：

- 白色与冷灰色为主背景，主色为接近 `#1769E0` 的专业蓝。
- “当前订单”是首屏的最强视觉元素，附近网点为第二层级。
- 底部固定导航为“首页 / 网点 / 订单 / 我的”。
- 首页快捷服务为“订单 / 取件 / 客服 / 帮助”。
- 状态绿色只表示在线、可用或成功；琥珀色表示余量不足、即将超时或需要注意；红色表示失败或阻断。
- 设计使用 8px 间距基线、12–18px 圆角和克制阴影，避免过度卡片化、装饰性 3D 素材和无关促销内容。

已批准视觉概念将作为实现基线。编码前需将其拆解为颜色、字体、间距、圆角、阴影和组件状态 Token。

## 4. 第一阶段增强功能

### 4.1 扫码找柜

首页和网点页提供扫码入口。扫码结果只接受本系统签发的柜机标识，后端解析并返回网点、柜机和在线状态。成功后进入对应网点详情；无效码、权限不足或设备离线时，允许重新扫描或查看附近网点。

### 4.2 消息通知

通知中心从个人中心进入，关键通知可同步发送微信订阅消息。第一阶段包含：

- 支付成功与柜格分配中。
- 存件成功与柜门已关闭。
- 即将超时和已产生补缴费用。
- 设备或开门异常。
- 取件完成与押金处理。

通知任务使用稳定幂等键，可重试但不重复投递。用户未授权微信订阅消息时，站内通知仍保留。

### 4.3 柜门安全提醒

开门指令成功不代表存件或取件完成。订单必须等待柜机上报门磁状态。柜门在限定时间内未关闭时，页面显示持续提醒、剩余处理时间、“我已关门，重新检测”和“联系客服”。安全提醒同时通过消息任务投递。

## 5. 前端技术架构

### 5.1 技术选型

- 小程序：Taro + React + TypeScript。
- 小程序构建：使用 Taro 当前稳定版支持的 Vite 构建方案。
- 管理后台：React + Vite + TypeScript，第二阶段启动。
- 状态：页面请求状态与服务端状态分离；只有需要跨页共享的用户、定位和活动订单进入全局状态。
- 接口：通过 Kratos Proto/OpenAPI 合同生成 TypeScript 类型，手写封装只负责认证、trace ID、错误映射和取消请求。
- 设计系统：小程序和后续管理后台共享语义化设计 Token，但不强制共享平台特有 UI 组件。

### 5.2 模块边界

```text
apps/miniapp
  app shell / routes / page composition
packages/api-client
  generated contracts / auth / trace / error mapping
packages/design-tokens
  color / spacing / typography / radius / shadow / state colors
packages/domain-ui
  money formatting / status copy / validation / view models
features
  location / sites / reservation / payment / storage / orders / pickup
  notifications / scan / door-safety / profile
```

页面只负责编排组件和触发用例。请求、状态转换、金额格式化、错误映射和幂等键生成不直接写在页面组件中。

## 6. 组件系统

首批实现以下组件族：

- 基础：Button、IconButton、Input、Search、Select、StatusPill。
- 反馈：Alert、Result、EmptyState、ErrorState、Skeleton、Toast、ConfirmDialog。
- 业务：CurrentOrderCard、SiteCard、LockerSizeCard、OrderCard、FeeSummary、StatusTimeline、DoorStatusPanel、NotificationItem。
- 导航：MiniAppTopBar、MiniAppBottomTabBar、FilterBar、BottomSheet。

组件的颜色、间距和状态必须来自设计 Token。业务组件接收已映射的视图模型，不直接依赖后端原始响应。

## 7. 数据流

### 7.1 查找与预约

1. 用户选择城市、定位或扫描柜机二维码。
2. 小程序请求网点和柜格可用量。
3. 用户选择柜格和时长，后端创建原子预约。
4. 预约返回稳定标识、过期时间和应付金额。
5. 前端倒计时只用于展示，预约是否有效以服务端时间为准。

### 7.2 支付与柜格分配

1. 前端使用业务请求 ID 发起支付，按钮在请求中禁止重复触发。
2. 前端支付结果不是最终订单真值，页面通过后端查询订单状态。
3. 支付成功但柜格分配尚未完成时，页面显示“正在分配柜格，请勿重复支付”。
4. 最终失败时显示联系客服和退款/人工处理状态，不允许直接重复扣款。

### 7.3 开门与关门

1. 前端请求创建幂等的设备指令。
2. 页面轮询或订阅指令与设备状态。
3. 指令成功后进入“等待用户放入/取出物品”。
4. 只有柜机上报门已关闭，服务端才推进订单状态。
5. 开门失败、设备离线或门长时间未关闭时，保留订单上下文并提供恢复操作。

## 8. 错误与异常状态

必须覆盖以下 12 类状态：加载中、空数据、网络失败、支付处理中、支付失败、支付成功、柜格竞争、设备离线、开门失败、柜门未关、超时补缴和权限不足。

每个失败状态必须显示：

1. 发生了什么。
2. 对当前订单或费用有什么影响。
3. 用户现在可以做什么。
4. 用于客服和排查的 trace ID，但不显示堆栈、token 或内部错误。

只有明确的安全操作才能自动重试。支付、预约和开门使用原请求幂等键，不创建新的重复业务。

## 9. 测试与验收

### 9.1 自动化测试

- 设计 Token、金额格式化、错误映射和状态文案的单元测试。
- 业务组件的关键变体与操作回调测试。
- 找柜、支付、存件和取件主流程的集成测试。
- 支付回调延迟、柜格竞争、设备离线、指令失败和柜门未关的异常测试。
- 通知任务的幂等、重试和站内消息保留测试。

### 9.2 视觉与交互验收

- 在微信小程序开发者工具中检查 375×812 基线屏幕和常见小屏设备。
- 逐页对比批准概念与实际截图，检查文案、布局、字体、颜色、间距、图标和状态。
- 所有主操作在单手可达区域，不存在横向溢出、文字裁切或遮挡按钮。
- 使用真实中文内容、金额、长网点名称和异常状态验收，不使用占位文字。
- 用户必须能从每个错误状态返回可执行的业务路径。

## 10. 交付标准

第一阶段完成需同时满足：

- 13 个页面均可从业务流程进入，无纯静态占位页。
- 找柜、预约、支付、存件、补缴和取件主流程可通过本地后端完整验证。
- 消息通知、扫码找柜和柜门安全提醒可演示正常与失败路径。
- 12 类必要状态有真实界面和恢复操作。
- 类型检查、单元测试、集成测试、小程序构建和视觉对比通过。
- 不将任何生产凭据、真实用户数据或未脱敏日志纳入前端代码、测试数据或构建产物。
